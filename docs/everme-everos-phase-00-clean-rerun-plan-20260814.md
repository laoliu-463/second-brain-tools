# EverMe / EverOS Phase 00 干净重跑方案

## 先看结论

现在不应该马上修 EverOS，也不应该进入 Phase 01。第一步是排除 Obsidian 自动保存对审计的干扰，重新拿到一份真正干净的 Phase 00 基线。

上次重跑中，A00 到 A11 都通过了。唯一失败的是 A12：审计期间，Obsidian 自己的工作区文件被写入，而冻结规则只允许写新证据和新审查页。

这更像审计环境干扰，不像 EverOS 故障。但目前只能确认 Obsidian 当时和现在都在运行，不能武断地说写入一定由它引起。因此下一轮仍要按最严格口径重新证明。

## 准备怎么处理

你先正常退出 Obsidian，避免未保存内容丢失。下一独立任务开始后，我只做以下事情：

1. 确认所有 Obsidian 进程已经退出；只要还有一个进程，就停止并报告阻塞，不强行结束它。
2. 为第二次重跑建立全新的证据目录和审查页，不覆盖前两轮材料。
3. 在开始时单独记录 Obsidian 工作区文件的状态。
4. 用本轮新证据重新执行 A00 到 A12。
5. 写完新审查页后，留出短暂静置时间，再复查一次工作区文件和整个允许写入边界。
6. 无论通过还是失败，都立即停止并交给你验收。

不会把 Obsidian 工作区文件加入允许名单。否则只是放宽规则，并没有真正解决问题。

## 这一步明确不处理什么

本方案不启用业务探针定时器，不替换健康检查文件，不调整服务器时间，不改 EverOS、Git、GitHub、Hook、服务或生产数据，也不做端到端记忆测试。

这些问题要等 Phase 00 真正通过后，再按下面的顺序分别立项：

1. 先核清两份健康检查文件哪一份才是批准版本；
2. 再设计并审批业务探针定时运行和健康检查接入；
3. 处理安装版本追溯和服务器时钟偏差；
4. 最后进入独立的业务链路验收阶段。

## 风险

- 退出 Obsidian 前如果有未保存内容，强行结束进程可能造成丢失，所以必须由你正常退出；
- 如果 Obsidian 退出后工作区文件仍然变化，说明还有别的写入来源，本轮会再次失败并停止；
- 即使 Phase 00 通过，也只代表基线和审计边界通过，不代表业务链路已经验收。
