# EverMe / EverOS 工程的 GitHub 管理方案

## 先看结论

服务器已经安装 Git，不需要重复安装。

但这次实测中，服务器虽然能打开 GitHub 网页，Git 拉取却失败或超时。本机的 Git、GitHub 工具、账号登录和网络都正常。因此我建议：

- 由本机负责建立版本记录、提交和推送 GitHub；
- GitHub 使用私有仓库；
- 服务器只接收经过确认的固定版本，不保存 GitHub 写入凭据；
- 暂时通过现有 SSH 连接，把本机导出的固定版本传到服务器；
- 不把服务器上的运行目录直接改成 Git 仓库。

这样既能马上建立可靠的版本记录，也不会因为服务器的 GitHub 连接问题卡住，更不会把线上数据库和日志误传到 GitHub。

## 当前已经确认的情况

- 服务器运行 Ubuntu 26.04，已经有 Git 2.53.0；
- 服务器没有 GitHub 命令行工具，但采用推荐方案后并不需要安装；
- 服务器能访问 GitHub 网页，说明不是完全断网；
- 服务器的 GitHub 拉取通道目前不稳定，本轮没有修改网络或认证配置；
- 本机已有 Git 和 GitHub 命令行工具，并且已经登录 `laoliu-463`；
- 计划使用的私有仓库 `laoliu-463/everme-everos-adapter` 目前还不存在；
- 当前适配器工程没有 Git 历史，这正是 Phase 00 无法通过的原因。

## 哪些内容进入 GitHub

只放能够重建和检查工程的内容：

- 适配器源代码；
- 测试；
- 部署脚本和安全的配置示例；
- 使用说明、验收说明；
- 明确的忽略规则。

以下内容一律不进入 GitHub：

- 真实配置、环境变量、Token 和密钥；
- 记忆数据库、状态数据库和备份；
- 日志、进程编号和运行缓存；
- 下载的模型文件和模型缓存；
- 本地审计证据 `.ecc`；
- 其他能够还原个人记忆内容或服务器现场的数据。

即使仓库是私有的，这些内容也照样不上传。私有仓库只是降低暴露范围，不等于可以存放密钥和记忆数据。

## 服务器以后怎样拿到版本

本机每次先完成修改、测试和提交，再从某个确定的提交导出发布包。发布包通过现有 SSH 连接传到服务器，并记录对应的提交编号。

服务器上的代码按版本单独存放。确认新版本可以运行后，再切换服务使用的版本。数据库、日志和真实配置继续留在独立的运行目录，不跟着代码覆盖。

如果新版本有问题，可以切回上一个版本。这个方式不依赖服务器直接访问 GitHub，也不会在服务器保存可向 GitHub 写入的账号凭据。

## 批准后怎样实施

下一任务只建立版本管理基线，不部署服务：

1. 再次核对忽略范围，并做一次敏感信息检查；
2. 给当前代码留存文件清单和指纹；
3. 在本机适配器工程建立 Git 仓库；
4. 创建第一条“当前现场基线”提交；
5. 创建私有 GitHub 仓库并从本机推送；
6. 重新克隆一份，确认 GitHub 上的内容能够还原工程，并确认没有运行数据和私密配置；
7. 把结果写成口语化页面交给你审查。

你审查基线没问题后，才另开任务设计和执行服务器的版本化部署。不会在同一个任务里顺手重启服务或替换线上代码。

## 需要特别说明的风险

第一次提交只能证明“从现在开始”的代码状态，不能补回之前已经丢失的修改历史。提交说明会明确写成“当前现场基线”，不会假装它是项目最初版本。

最大的实际风险不是 Git 本身，而是第一次提交时误带运行数据或凭据。因此必须先做忽略检查和敏感信息扫描，检查通过后才能推送。
