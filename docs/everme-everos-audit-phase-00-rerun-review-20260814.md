# EverMe / EverOS Phase 00 重跑审查

## 结论

这次 Phase 00 重跑没有通过。A00 到 A11 都拿到了本轮新证据并通过，但 A12 的“只在指定位置写文件”门禁失败了。

失败原因不是 EverOS 服务再次出故障，而是审计期间发现 Obsidian 的工作区文件被自动写入。这个文件不在本次允许写入的两个位置里。虽然看起来像 Obsidian 自己保存界面状态，但现有证据不能排除它和本次新增审查页有关，所以不能硬判 A12 通过。

## 这次新确认了什么

- 本机可以正常通过指定 SSH 别名连接服务器。
- 适配器项目路径正确，当前本地版本就是已批准的基线版本，和 GitHub 上的主分支一致。
- 项目里没有已暂存改动、源码改动、冲突或未跟踪文件。被 Git 忽略的内容已经分成运行数据、工具缓存和历史审计材料，不当成源码变化。
- 当前 Codex Desktop、Claude Code 和 EverOS 的版本及安装位置都已重新确认。
- 本机和服务器的关键配置及运行控制文件都重新计算了指纹，没有读取或保存密钥内容。
- 审计前后的关键配置、项目版本、服务进程、计划任务和生产数据指纹一致。唯一破坏门禁的是 Obsidian 工作区文件在审计窗口内发生了写入。

## 为什么这次不能算通过

冻结规则要求本轮只能写新证据目录和这张审查页。实际检查到 `workspace.json` 在审计期间被更新，因此无法证明写入边界完全守住。这个文件没有被回滚，也没有继续调查或修复；本任务按规则在这里停止。

## 仍然需要注意的地方

- 业务探针的定时器仍处于未启用状态。探针文件虽然在，但不会按计划自动运行，业务级故障可能无法及时暴露。
- 服务器上正式使用的健康检查文件，与临时目录中的候选文件不是同一版本。当前只确认了两者不同，不能擅自判断该保留哪一个。
- EverOS 当前版本和安装位置可以确认，但安装现场没有足够信息把它追溯到某个具体源码提交。
- 服务器虽然显示时间同步正常，但实测比本机慢约一秒。做秒级日志对照时需要把这个偏差算进去。
- 本轮没有检查真实 Hook、MCP、Flush、召回或跨端记忆效果，所以不能据此宣称整条业务链路已经健康。

## 这次明确没有做什么

本任务没有主动执行修复、部署、重启或重载，也没有改代码、Git、GitHub、Hook、计划任务和生产数据，没有写入测试记忆。需要单独说明的是：Obsidian 自动写入了自己的工作区状态，这正是 A12 失败的原因。Phase 01 没有开始。
